# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

University project (PUC-Rio, Distribuição e Concorrência, enunciado `Trab1_2026-1.pdf`): a "SmartFactory" IoT simulation on a 3-broker Apache Kafka cluster (KRaft mode, no ZooKeeper) run entirely via Docker Compose. Code, comments, logs, and docs are in Portuguese; keep new text in Portuguese to match. The assignment says "não invente": every log under `reports/logs/` must be produced by a script run, never written by hand.

`docs/ROTEIRO_DE_EXECUCAO.md` maps each item of the assignment to where it is implemented and how to demonstrate it; keep it in sync when behavior changes.

## Commands

All via `make` (requires Docker + Compose v2, bash 3.2-compatible scripts):

- `make build` / `make up` (build, start brokers with `--wait` on healthchecks, create topic, start everything) / `make down` / `make clean` (`down -v`, wipes Kafka data and alerts)
- `make logs`, `make alerts`, `make health`
- `make scale-consumers N=5`, `make scale-down`/`scale-up`, `make scale-sensors N=8` (extra sensors, compose profile `scale`)
- Tests (each writes evidence to `reports/logs/` and exits non-zero on failed assertions): `test-cluster` (T0), `test-balance` (T1), `test-consumer-fail MODE=graceful|hard` (T2), `test-broker-fail MODE=graceful|hard KIND=controller|follower` (T3), `test-load` (T4), `test-elasticity` (T5), `test-sensors` (T6), `test-two-brokers` (T7), `test-alerts` (T8), `capture-pcap` (T9), `unit-test` (T10, runs `tests/` inside the consumer image), `test-all`, `evidence` (clean + up + test-all)

Scripts run from the repo root and share `scripts/lib.sh` (asserts via `check`, Kafka helpers that run the CLI tools inside a live broker container). Re-running a test overwrites its log, so only regenerate committed evidence deliberately.

## Architecture

- **`docker-compose.yml`**: YAML anchors (`x-kafka`, `x-kafka-env`, `x-producer`) define three broker+controller nodes (`kafka-1..3`, `apache/kafka:3.7.0`, healthchecked), four sensor services, `sensor-extra` (profile `scale`, `SENSOR_ID` derived from hostname), and `consumer` (`deploy.replicas: 3`). The producer image is built only by the `producer-image` service (profile `build`) to avoid the same-tag build conflict; `make build` uses that profile.
- **Config**: `config/sensor_thresholds.env` is the single source (compose `env_file`, Makefile `include`, scripts `source`). Per-sensor profile (`SENSOR_ID`, `TEMP_BASE`...) is in compose `environment`. `PROCESSING_DELAY_MS` lives in compose (overridable per run by the elasticity test). Broker replication settings are literal in `x-kafka-env` and must stay coherent with `TOPIC_*` in the env file (T0 asserts this).
- **Producers** (`producer/sensor_producer.py`): `acks=all`, message key = `sensor_id`. The four fixed sensor IDs were chosen (via murmur2) so all 3 partitions receive data; changing an ID can leave a partition empty (`make test-balance` catches it).
- **Consumers** (`consumer/data_processor.py`): one group `smartfactory-processors`; `SmartFactoryRebalanceListener` prints REVOKED/ASSIGNED banners used as evidence; severity from env thresholds; non-normal events appended as JSON lines to `ALERT_LOG_PATH` (shared `alerts-data` volume).
- **Clients** (`kafka-python-ng==2.2.3`): both use exponential-backoff connection retries and a short `metadata_max_age_ms` (10 s). Without it, after a hard kill of the KRaft controller leader the clients kept stale partition leaders and stalled or dropped batches (found by T3). `PRODUCER_REQUEST_TIMEOUT_MS` must exceed the controller failover time (~15 s).
- **Failure modes**: `docker stop` (graceful, consumer sends LeaveGroup, immediate rebalance) differs from `docker kill` (hard, detected by `session.timeout.ms`). Hard mode uses `docker update --restart=no` first, otherwise `restart: unless-stopped` revives the container.
